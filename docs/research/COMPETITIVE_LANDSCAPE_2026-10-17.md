# CommonReel 竞品重叠与可拓展工作流

调研日期：2026-10-17（Asia/Shanghai）。本笔记核对竞品官网和 CommonReel 当前源代码。竞品条目均为官方公开介绍，本轮没有注册、操作或独立验证其完整产品流程；宣传中的速度、准确性和公平性不当作实测结果。未在官网找到的能力记作“未确认”，不能推导为竞品没有实现。本文评估产品区分度，不承诺原创性、专利性或获奖。

## 2. CommonReel 现在确实有什么，能说明什么

当前源码的硬筛选、每人估计及排序位于 [selection.go](../../internal/workflow/selection.go)。片长、类型否决、禁止重看及美国订阅供应属于资格条件；排序默认采用 `0.65 × 成员最低估计 + 0.35 × 成员平均估计`。硬条件不会因总分高而被覆盖。这个实现便于复算，但它是启发式群体估计，不能据此声称公平得到证明、模型更懂人或实际满意度更高。

有价值的现有组合是：硬条件与估计分数分离、供应事实有时效、保存前重新查询、变化时使旧选择/逐成员接受失效、模型工具调用来源可见、模型失败可继续操作页面。这些是可演示的工程资产；用户是否在意、是否优于直接投票仍待验证。[当前候选校验](../../internal/workflow/current.go)、[保存与失效处理](../../internal/workflow/workflow.go)、[Go 事实说明](../../internal/workflow/grounding.go)、[当前证据状态](../IMPLEMENTATION_STATUS.md)。

两项当前限制会影响拓展：

1. 现有目录是有边界的电影集，当前 217 部的年份为 1968–1996，所有 `catalog_prior` 均为 3.0；评分主要来自明确评分/喜欢类型与这个先验。没有足够明确偏好时，多部电影会同分，不能包装成掌握全部电影或完整个人口味的模型。[当前目录](../../assets/catalog-v2.json)、[评分与目录响应](../../internal/workflow/selection.go)
2. 当前 `eligibility` 返回影片遇到的第一个失败原因。因此页面的各类排除计数可以解释首个筛除步骤，不能直接当作完整冲突集合，更不能证明某项条件是唯一阻碍。当前供应探测也受每轮 30 部与超时限制；未查到不等于不可看。[现有筛选与探测循环](../../internal/workflow/selection.go)

## 3. 拓展方向 A：选不出时，做有边界的反事实协商

真实场景是大家已表达了限制，结果为零。再生成几个片名或让某人随便选，无法说明到底应改变什么。可以把工作流扩成：辨别已知冲突与资料未知 → 在不改状态的试算区生成少量可行调整 → 展示每项具体牺牲和新增候选 → 小组明确采用一项 → 再次核验并重新收集条目接受。

最小实现建议：仅允许对小组主动标记为“可讨论”的条件试算，例如片长上限或本次重看开关；未获允许的否决和平台集合保持锁定。Go 在有界目录上枚举一项或最多两项调整，逐片计算所有约束，或对每个假设补丁重新运行共享的权威资格判断；模型负责问清含义和解释，不负责编造冲突。推荐修改不能静默生效。

界面应分别展示“当前已确认可行 0 部”“还有多少部因资料未确认未能判定”“如果采用调整 X，按现有事实增加 Y 部”。只有对调整后的完整约束验证通过且供应仍新鲜的电影，才能计入确认可行数。不要把有待查询的电影算作已经解决冲突。

如果叫“最小调整”，必须写明最小的定义，如先最少改变条件数量，再比较新增分钟数；没有用户给出的可比成本时，不应自称找到了小组损失最小的方案。存在多个同样小的方案，应并列展示，而不是隐含偏袒某位成员。当前允许代填/代决定的语义继续保留，结果只能叫小组记录的选择。

它与本轮官网常见路径的可见区别是提供可核对的调整方案及其后果，而不只展示投票结果、转盘或下一组卡片；这只是可见工作流区分，不能据此认定其他产品没有同类内部功能。该方向可通过固定目录、确定供应快照和冲突场景构造工程证据，不需要先取得大规模用户数据。

## 4. 拓展方向 B：在供应额度内，先核查真正可能救活选择的缺失资料

真实场景是条件本身可能有解，但平台数据未查、超时或过期。单纯显示“无结果”会把数据不完整误读为偏好不合。当前代码已在本地硬条件通过后再探测供应，但每轮按目录顺序选择最多 30 部，优先级仍有改进空间。[shortlist 实现](../../internal/workflow/selection.go)、[供应额度保护](../../internal/workflow/watchmode.go)

可拓展为：先按已知硬条件筛选 → 把未知供应的候选按本地估计、缓存年龄与已核查覆盖情况排序 → 给本轮设定明确查询预算 → 只补查最有希望或能区分两条方案的影片 → 根据返回事实更新可行集合。预算用完、供应商错误和确认不可用分别显示。

最小交付可以先是透明的确定性优先队列，无须宣称“主动学习”或“最优信息增益”。如果只用预测分数挑选，可能放大已有偏见；可加入覆盖不同成员口味的简单名额，并记录选取理由。模型能解释待核查项，但不得决定绕过配额或把未知供应变成已知供应。也不能查任意数据源来规避供应商条款。

这项方向较适合展示 Go 并发、缓存和预算管理能力，但单独拿作产品卖点较弱。评估应比较相同调用预算下的确认可行数量、首个可行候选出现所需查询数、重复查询数与配额违规次数。离线回放可以用完整已知的供应快照提供参照；实时只查询一部分时，不能声称知道全部正确答案或全局最优。

## 5. 拓展方向 C：临门一脚不能看时，救回这场电影夜

真实场景是小组已经记录接受，点击保存时发现供应失效或选中平台不再提供。当前系统会重新查询并让失效选择和接受记录失效；这是已有安全底座，尚可拓展成用户能继续走下去的恢复流程。[保存前核验与 invalidateSelection](../../internal/workflow/workflow.go)、[事实版本与失效函数](../../internal/workflow/selection.go)

可拓展为：明确提示发生了什么变化及核查时间 → 保留仍有效的当晚片长、平台、否决、已看等输入 → 在原硬条件下找替代候选 → 说明替代片与原选择的差异 → 重新记录逐成员条目接受 → 再核验并保存。不能把对旧片的接受迁移到新片，也不能为救场自动新增平台、允许付费租赁或取消否决。

如果没有符合条件的替代片，才进入方向 A 的显式协商；如果只是供应不确定，先进入方向 B 的预算核验。一个可演示的闭环由此形成：资料未知时查证，确知冲突时协商，事实变化时恢复。

该方向离现有实现最近，增加的是有目的的恢复路径和变化解释，而非重造推荐算法。它能在短演示中形成清晰前后状态，但真实供应变化不受现场控制。应同时保留真实 API 成功证据与明确标注的供应失效回放；回放不能冒充比赛现场恰好发生的真实下架。

## 6. 取舍与验证建议

| 方向 | 用户可见性 | 现有实现可复用度 | 最值得证明的事情 | 不应作出的宣称 |
| --- | --- | --- | --- | --- |
| A 有边界协商 | 高，能直接看见为何无解及改变后果 | 中，需要补全约束失败集合及试算接口 | 无修改试算、所有候选重新满足完整条件、明确应用后旧接受失效 | 首创协商算法、保证全员公平、实际节时比例 |
| B 定向查证 | 中，需把未知和预算显示清楚 | 中高，可复用缓存、额度与并发槽 | 同预算可重复对照、请求上限、未知不误判 | 免费额度无限、全目录供应实时、全局最优查询 |
| C 失效救场 | 高，故事具体、容易观察 | 高，已有保存前核验及版本失效 | 硬条件完整继承、接受不跨影片迁移、过期结果不能覆盖当前房间 | 永久保证可播放、回放等于真实下架、自动替用户同意 |

在比赛前的有限时间内，优先让 C 成为完整故事，或让 A 成为一个受控范围内完成的主场景；B 作为两者需要的查询机制逐步加入。三项同时做大，会分散原有闭环的可靠性。新的主张可以是“帮助小组处理选不出和已选失效，并让每次改变都有事实依据”，但应先用工程证据支持，再由真实小组验证其价值。

当前最可用的优势不是某项孤立功能，而是已有 Go 状态一致性、供应事实边界与模型执行约束，能把上述失败恢复做成可核验的流程。能否形成用户优势和比赛区分度，仍取决于完整演示、评审要求及后续观察。本轮没有证据支持“别人做不到”或“采用某方向就能得奖”。
