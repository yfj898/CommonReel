# CommonReel 差异化与扩展建议

日期：2026-10-17。基于当前源码 `a9b85b9`、本地数据检查和一手产品资料。本文件是策略提案，不修改已确认的需求，不表示下面的功能已经实现。竞品页面属于厂商公开描述，未逐个实测；没有公开描述不等于没有该功能。

## 核心判断

现在的优势是可复核的多人状态处理、真实 MCP 工具链、确定性的资格检查与失败处理。这些能力已经形成工程成果，但还需要转化成用户能直接使用、评委能直接看见的产品行为。房间、免登录加入、类型否决、平台筛选、历史导入和推荐解释，都不足以单独支撑明显的差异化。

建议以“电影夜协商助手”为下一阶段主线：在选不出、资料不足或已选影片失效时，说明原因，计算有依据的下一步，并等待小组明确决定。主打无结果后的协商，配合有针对性的数据补查。跨场次公平与通用协商框架保留为后续方向。

这提高的是差异化的可见性和论证力度，不是获奖保证。当前比赛作品画廊未公开，无法比较完整参赛阵容或估计获奖概率。[官方画廊](https://amazonappdev2026.devpost.com/project-gallery)

## 比赛实际看什么

官方第二阶段把技术实现、设计、潜在影响、创意质量列为同等权重。对 Alexa+，官方将单轮问答和基础 API 包装列为普通例子，把有状态的代理流程、媒体卡片、MCP Apps 等列为创意方向。具备 MCP endpoint 证明技术路径可运行，不能自动证明创意突出。摩擦日志可获最高 10% 加分，仍由评审决定。[官方规则，第 6 节](https://amazonappdev2026.devpost.com/rules)

据此形成的内部判断是：工程证据相对充分；设计已有完整闭环，但尚无真人可用性验证；潜在影响缺少直接用户证据；创意容易被“多人电影推荐”这个宽泛类别稀释。这里没有给出伪装成官方结果的分数。

## 现有优势如何变成产品价值

| 已有积累 | 当前证据 | 可让用户直接感受到的价值 |
|---|---|---|
| Go 统一业务模块，网页与 MCP 走同一规则 | `internal/workflow` 与验收记录 | 助手承诺和页面最终结果一致；调整条件后大家讨论同一份候选 |
| 双版本、CAS、响应失效、保存前供应刷新 | `workflow.go`、`selection.go`、测试 | 有人临时改变条件或供应失效时，阻止过期选择并提供继续协商的入口 |
| 真实失败后的 Go grounding | `evidence/agent-real-v2-before-grounding.json`、`agent-ui-refresh.json` | 影片能否看、需要多久、为什么满足条件有实际来源 |
| 本地目录、规范化 CSV、恢复码画像 | 导入与生命周期实现 | 可复用自己的资料，同时区分看过、喜欢和今晚想看 |
| 供应配额、未知值排除与缓存 | `selection.go` 与供应商 adapter | 诚实说明哪些已确认、哪些值得再查，不把未知包装成不可看或可看 |

Go、SQLite、MCP、本地模型和深色界面都可以被其他团队采用。更有意义的组合是把这些部件用于一次可完成、可解释、能从失败中恢复的共同决定。

## 数据与推荐区分能力的实际短板

当前 `assets/catalog-v2.json` 有 217 部电影，年份为 1968–1996；217 个 `catalog_prior` 均为 3.0。检查记录见 `research/CATALOG_DIFFERENTIATION_AUDIT_2026-10-17.json`。

`selection.go:324` 的估计规则优先使用明确评分；没有评分时，类型命中增加 0.3，否则返回先验。因此，没有评分且没有正向类型命中的成员，对这些影片的估计都会是 3.0。换一个最低分/平均分聚合公式，不能补出缺失的偏好证据。这是代码和数据推导，不是推荐准确率实验。

建议保持已确认的 200–300 部有边界目录，更新一部分近期影片与常见片型，并保留稳定标识和真实供应核验；不追求无依据的“全网覆盖”。另一种定位是明确服务经典电影小组，但这需要对应的用户证据。冷启动可只问一个有实际影响的类型偏好问题，允许跳过，不把“选了某片”伪造成五星评分或喜欢。

## 发散方向与取舍

| 方向 | 具体使用价值 | 复用程度与主要成本 | 建议 |
|---|---|---|---|
| 无结果后的条件试算 | 看见明确调整后能找回哪些已核实候选，保留其他限制 | 高复用；需只读试算、组合阻碍检查、显式应用与过期保护 | 第一主线 |
| 有针对性地补查资料 | 先查符合其余条件、仅供应未知的影片，显示本轮调用预算和结果 | 高复用；需候选探测顺序、明确预算和限额失败处理 | 第一副线 |
| 选择失效后的恢复 | 保存时供应消失，保留当前小组条件并找其他候选，逐人重新记录接受 | 高复用；需恢复状态与可理解的界面说明 | 主线完成后补充 |
| 冷启动主动询问 | 在大量 3.0 并列时，用一个可跳过的问题收集明确偏好 | 高复用；需证明问题对当前候选确有区分，不伪造评分 | 基础修正 |
| 多轮电影夜的妥协记录 | 观察多次明确反馈中谁经常不满意，再讨论轮换 | 当前匿名摘要不足；需要新增长期小组关联和反馈授权，不能用代填接受代替满意度 | 后续探索 |
| 对话内可操作卡片或 MCP App | 在讨论旁直接查看试算与影片，不在聊天和页面之间反复找 | 普通网页卡片可先做；正式 MCP Apps 需宿主能力检测、真实 UI 资源和桥接验证 | 展示增强，避免抢占主线 |
| 开源通用协商模块 | 把资格判断、只读试算、版本化应用和回执抽成可复用模块 | 抽象与独立示例需要额外工作，真实第二场景应先证明复用需求 | 比赛后或主线稳固后 |

MCP Apps 是扩展，需要支持它的宿主，不能由 MCP 核心协议版本推断已经兼容 Alexa+。本项目现有网页卡片也不能直接称为 MCP App。[MCP Apps 官方文档](https://modelcontextprotocol.io/extensions/apps/overview)

长期公平本身已有研究，不能仅凭“轮流照顾不同成员”就宣称新算法。若探索，应报告自定义目标、明确反馈和离线实验范围。[Fair Sequential Group Recommendations，作者版本](https://homepages.tuni.fi/konstantinos.stefanidis/docs/sac20.pdf)

## 推荐主线的最小范围

建议工作名称为“看不到合适电影时，下一步怎么选”。用户场景仍是同地的 2–4 名成年人。

1. 用户得到空候选时，同时看见“已核实但不满足”和“供应未知”两类状态。
2. 页面询问哪些条件愿意讨论。类型否决默认不动；不建议新增付费订阅；供应和元数据未知不能通过修改偏好变成已确认。
3. 只读试算最多展示三项可核对方案。每项列出准确变化、保持的条件、已核实可恢复影片及仍需补查的影片。所有数字由 Go 重算，不由模型编造。
4. 用户明确应用某一方案时，复核房间/决定/事实版本。若其他成员已改条件，拒绝旧方案并重新试算。应用后旧候选和接受记录按现有规则失效。
5. 若没有已核实方案，只提供有限的补查入口或明确说明当前边界；不反复生成貌似有结果的文字。

### 实施时必须保留的准确性

- 当前 `eligibility` 在首个失败原因处返回。现有过滤数量不能当作所有冲突原因，也不能推出调整一项就能恢复几部电影。试算必须收集组合阻碍，或对每个假设完整重跑同一权威判断。
- 必须列出多条件同时阻碍的情况。只放宽时长仍被否决的影片，不算恢复。
- 只读预览不修改房间、不写长期画像、不自动消费供应额度。需要补查时由明确操作触发有限请求。
- 试算结果仅适用于当前目录、当时有效事实与允许的变更集合。首版可只搜索有界的单项或两项变化，不声称找到全局最小让步。
- 恢复影片数量在截断为最多六个展示候选之前计算，避免把展示上限当成实际可行数。
- 不能将某位成员的限制描述成过错。采用“这些条件组合尚无已核实候选”的表述。
- 模型负责理解和组织工具调用；Go 返回精确方案、版本及事实，最终操作保留用户明确动作。

### 工具与接口草案

可以增加一个只读 MCP 工具 `plan_adjustments`，传入明确允许调整的字段与有界范围，返回基础版本、方案 ID、精确 patch、恢复影片和未知项。是否增加以及最终名称仍属后续 spec 决定；若增加，工具数量、白名单、界面徽章及文档需同步。

显式应用应走现有页面命令的事务边界，并携带预览依据的版本。首版不把保存、接受、画像维护交给代理。

## 怎样建立证据

先构建可复现的真实目录加构造条件测试集，覆盖单项冲突、多项冲突、未知供应、全部禁止调整、资料过期和并发输入改变。测试目标应报告分子和分母，不提前写改善百分比。

比较基线为“当前空结果说明加手工修改”，对比方案为“相同目录/事实下的只读试算加显式应用”。可测正确恢复数、违反未授权硬条件的次数、未知误当已知的次数、每次方案所需外部调用数、失效预览被正确拒绝的次数。所有构造测试仍是工程证据，不能称作真人讨论轮次、满意度或节省的选片时间。

小组接受、观看和满意度是不同事件；保持既有代操作记录语义。用户暂时没有测试者，文档不把脚本测试改名为用户研究。

## 评委能看懂的三分钟故事

建议把演示从正常创建房间，改为一开始就显示一个真实可复现的分歧场景。

| 时段 | 可观察行为 |
|---|---|
| 0–20 秒 | 两人的条件组合得到零个已核实候选，界面解释覆盖边界 |
| 20–65 秒 | 用户明确说“否决不动，片长可以讨论”，代理调用只读工具，显示带准确影片与事实的试算 |
| 65–105 秒 | 一个方案展示时，另一端修改条件，旧方案被拒绝并重新计算 |
| 105–145 秒 | 用户应用新方案，提出候选，收齐可代填记录，保存前再次核验供应 |
| 145–170 秒 | 显示真实工具来源、源码和测试证据，说明模拟及用户验证边界 |

以上是待实现的演示脚本，不是当前录像内容。优先录制实际点击与状态变化；截图旁白可以作为备用材料。

## 截止前的建议顺序

先做目录与冷启动修正，再完成“空结果—只读试算—显式应用—过期拒绝”一条完整路径。完成这条路径后，再决定是否加入有限补查或失效恢复。给重新录制、公开上传和 Devpost 检查留出独立时间。

不建议同时新增完整语音栈、原生电视应用、购买流程、跨国家供应或多个业务领域。它们会增加新的接入和验证工作，当前差异化主线尚未完成。

可用于对外验证的新定位草案：

> CommonReel helps a group understand why movie night is stuck, explore verified alternatives, and explicitly agree on the next step.

定位中的新能力必须在实现后才能进入最终参赛说明。当前仍应沿用已有项目的真实能力描述。
