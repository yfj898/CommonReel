# 比赛要求、使用场景与需求复核

核查日期为 2026 年 10 月 13 日。本文是产品分析，用户画像、目标和后续实验均需验证。
当前工程证据来自仓库文件及既有报告，本轮没有把研究画像或离线指标认作真实用户效果。

## 结论

Amazon Build, Ship, Shape 要求围绕指定设备或开发能力构建完整体验。
CommonReel 的 Go MCP 服务已经提供工程基础。当前主要缺口是实际成员的偏好获取、
今晚可观看的内容约束、自然语言协商，以及群体选择效果的直接验证。

建议先验证一个窄场景。两至四名成年用户在同一客厅，希望较快决定今晚能够观看、
每个人都愿意接受的一部电影。人数与目标是产品假设，尚无本项目用户研究支撑。

## 官方要求

主赛道包含 Fire TV、Alexa+、Bee、Ring。Fire TV 强调电视上的消费体验；Alexa+
提供 MCP/Agent Skill 或网页模拟路径；Bee 需要真实设备产生的数据；Ring 可以
使用官方设备或模拟器。参赛只需选择适合的主赛道，附加奖项另有要求。

Alexa+ 的 MCP 路径要求 2025-11-25 或后续确认版本及 Streamable HTTP。
网页模拟路径允许使用自选 AI/agentic 工具，无特定 SDK 或 MCP 表面要求。
自托管 MCP 的协议测试和浏览器模拟不能建立真实 Alexa 设备认证或上线状态。

评审先判断基本可行性和赛道契合，再按四项同等权重评分。技术实现、设计、潜在
影响、创意质量都需要证据。官方把单轮问答和简单 API 包装列为普通方案，把跨
服务工作流、跨会话状态和媒体交互列为更有创造性的方向。这些是方向示例，
没有要求同时实现所有能力。

交付包括实际运行的代码及说明、可访问仓库、三分钟以内公开演示视频、工具使用
反馈和赛道标识。材料须使用英文或提供英文翻译。仓库可以公开并带开源许可，
也可以私有并共享给指定评委。主办方拥有资格与评分裁量权，不能据本地测试
宣称正式参赛审查已经通过。

提交截止为北京时间 2026 年 10 月 24 日 03:00。

## 现实依据与现有能力

Amazon 已提供影视推荐与个性化能力；其最新 Fire TV 公告还说明订阅、观看历史、
可看性、追问和跨设备会话等方向。部分新功能计划从十一月开始在美国分批推出，
不能把公告视作当前所有设备都可用。

Netflix 的推荐系统已利用观看行为等信息做个性化。更早的 PolyLens 原始研究
已经讨论多人电影推荐、组内权利、隐私和群体聚合，并进行了长期用户试用。
多人推荐、协同过滤及照顾最低预估分已有先例。当前公式不能作为新算法主张。

上述资料支持继续研究群体选择，但没有证明我们目标用户的痛点频率、支付意愿、
使用频率或对当前实现的需求。也没有证明 Alexa+ 缺少类似群体功能，须直接比较。

## 需要验证的需求

| 用户任务 | 对产品的要求 | 当前状态 |
|---|---|---|
| 少花时间找到共同接受的影片 | 少量候选、渐进澄清、直接确认 | 有六部片单；选片时间未测 |
| 让每个人都能表达限制 | 偏好归属明确、否决由本人控制 | 能编辑成员；所有房间链接持有者可编辑所有成员 |
| 不重新填写一长串资料 | 当晚偏好、少量喜欢的影片、可选历史 | 真实历史获取缺失；研究 profile ID 只适合演示 |
| 今晚确实能够观看 | 地区、订阅、额外费用、可看性 | 没有接入 |
| 适合当晚情境 | 时长、情绪、是否重看、语言等约束 | 仅有类型和此前评分排除 |
| 修改条件后继续协商 | 保存上下文、解释变化、避免混淆成员 | 有房间状态；对话仅支持四种固定意图 |
| 看到可信的推荐理由 | 来源事实、估计与未知值分开 | 有评分解释；不能代表本人意愿 |
| 从协商走到决定 | 成员确认、保存片单、可行的观看入口 | 保存由一次点击完成；没有逐成员同意或观看入口 |

研究标签上的 Horror 否决不能充分表达用户说的“不想被吓到”。没有剧情或内容
分类数据时，不应把类型过滤描述成完整的内容适宜性判断。

## 建议的目标体验

用户提出“今晚三个人一起看，九十分钟左右，想轻松一点，不想额外付费”。
助手确认成员和各自限制，获取真实偏好，查询经授权的片长及地区供应数据，
保留满足条件的影片，给出三项候选与简短权衡解释。有人改变限制时只更新
相关条件，无法满足时说明冲突并征求调整。成员确认后保存共同选择。

这条路径是建议设计，当前尚不能完成片长、费用和供应查询，也没有真实模型
完成开放式意图解析。原型的研究历史不能自动映射到当前来访者。

TMDB 的官方 watch/providers 接口可按国家查询平台供应信息，数据来自 JustWatch，
需要相应署名和账号权限。该接口不返回完整播放深链接。供应结果也不等于确认
某个用户账户的权益，不能直接承诺免费播放或设备自动播放。

## 下一步的顺序

1. 先观察三至五个真实小组过去一次实际选片过程，记录重复摩擦、输入成本和已有
   替代方式。这是探索样本，不是代表性用户统计。不要先向参与者推销“公平算法”。
2. 让新用户通过少量实际喜欢的影片和当晚限制进入流程，移除研究 ID 的产品入口。
3. 缩小到一批可核对的内容，补片长、地区、供应与更新时间，缺失值明确标为未知。
4. 测试有上下文的多轮工具编排。成员身份或偏好归属不明确时追问；共享选择需要
   清楚的同意机制，持续偏好与当晚限制分开。
5. 与同样信息条件下的热门片单、平均聚合、简单投票，以及可访问的原生助手比较。

主要结果记录选定且全员接受的比例、达成选择的用时、重新筛选次数、实际限制
违反次数、推荐内容可看性、偏好录入耗时和是否愿意再次使用。愿意看是一类结果，
看完后的满意是另一类结果。多人试验应按组和任务记录，并平衡条件顺序。

当前 NDCG@10 0.1566 对 0.1316 证明的是固定离线协议中的单人排序差异。
它不能代替以上用户结果，最低预测分变高也不能直接证明群体更满意。

止损条件需在实验前确定。若加入偏好所需时间超过节省的决策时间、简单投票或
现有助手同样有效、目标小组很少有共同选片场景、供应数据无法可靠获取，应该
缩小定位或重新选题，不用更多模型和工具掩盖这些问题。
